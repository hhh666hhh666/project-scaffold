# 测试体系模板：搬了什么、明确不搬什么

## 一、搬了（F3a：规范与机制）

`--with-testing` 生成 `docs/testing/README.md` + `docs/testing/系统说明.md`。两份分工是通用的：
**现状与清单只写一次**（README），**理由只写一次**（系统说明）——同一件事写两遍必然漂。

保留下来的通用件：

| 部件 | 为什么通用 |
|---|---|
| 三层定义 + 「每层独有的问题」 | 加一层的判据是「它能回答一个别层问不出的问题」，说不出口就不该加 |
| **「改动 → 补哪层」映射表** | 改接口 / 改核心规则 / 改库结构 / 改界面 / 升级依赖 / 只改样式 / 只改类型 / 只改 CI——都是通用判据 |
| 「对应测试进同一个 PR」 | 上下文一散，补测试就永远不会发生 |
| 「什么不用补」反向清单 | 否则每个改动都背上「必须写测试」的包袱 |
| 「能保证 / 不能保证」表 | 防止「有了测试就等于都对了」的错觉 |
| 「明确不做」清单 | 已定边界写在明处，才不会反复纠结 |
| 机械守卫的作用**与局限** | 它只验「有没有测试类」，验不了「断言到没到点子上」——这条必须写，否则会被当成质量保证 |
| 术语表 | 「接口测试」和「服务集成测试」不要都叫「集成测试」 |

**不搬具体业务**：源项目写的是「只测判分与导入校验」，那是它的业务选择。
模板改成**判据**：「**只测静默错误**——错了不报错、只会一直错下去的那种逻辑」。

**分层命名约定**（`*Test` 归单元、`*IT` 归集成）写在测试文档里，构建工具那段配置由后端模板的 pom 出，两边不重复。

### 组件测试范本：为什么骨架就带

骨架原先只给前端逻辑单测（请求层、登录态、路由守卫），组件测试的触发条件写成「多个页面复用同一段自研逻辑或纯逻辑密度显著上升」，骨架阶段不成立。现在提前纳入**一个组件测试范本**：页面即将成为代码主体，没有范本时开发者不会自发写组件测试，等到「触发条件成立」那天也已经欠了一堆页面测试。

范本只演示**组件状态与数据流的衔接**（加载中 / 成功 / 失败三种显示），不引入浏览器、不引入视觉回归、不引入 e2e；请求用假函数替掉，组件测试仍然随手能跑。取舍同时写在生成项目的 `docs/testing/系统说明.md` 里。

**被否的方案**：

- **继续只测纯逻辑，等触发条件成立再补**：条件要靠人判断，而「新项目没有业务之前不需要」在页面铺开之后就不再成立——届时没有可抄的形状，测试会长期缺席。
- **一步到位上 e2e**：强绑定具体业务场景与运行环境，骨架没有业务可测；维护成本远高于收益。

**后果**：前端测试从「纯逻辑」变为「逻辑 + 组件状态」，盲区缩小到「交互路径与视觉表现」；多一个开发依赖（`@vue/test-utils`），版本登记进版本表；组件测试也归 `npm run test`，门禁数量不变。lint、视觉回归、跨浏览器、e2e 的立场不变。

⚠️ **这条决策的存档在本文件，不写进生成项目的 `docs/adr/`。** 那是新项目自己的决策地，且骨架阶段必须保持空目录（只留 README），否则会占用它的 0001 编号，并把脚手架的历史写进新项目。

## 二、明确不搬（两条，理由写在模板里防止被当成遗漏）

### F3b · 端到端（e2e）跑法

**不进模板。** 源项目的 e2e 工程全文绑定具体场景与运行环境：

- 前端 preview 必须 `--host 127.0.0.1`（Linux runner 上 `localhost` 解析成 IPv6 的 `::1`，只监听 `::1`，
  于是 curl 127.0.0.1 每次「0ms 直接拒绝」——看起来像服务没起来）；
- 本机直驱浏览器（不下载 Chromium，用 CDP 连本机 Chrome）；
- 一次性 MySQL 容器的起法与等待逻辑；
- 页面里的定位钩子（`.qb-row` 之类）与测试专用账号。

**剥掉这些之后所剩无几**；而且**新项目在还没有业务之前并不需要 e2e**。
模板在测试文档里显式写了这条边界声明（「不提供端到端工程的跑法模板」）。

### AI 探索测试

**整块剥离**——源项目的 `docs/testing/agent-exploration.md` 不进模板，且模板里
**连「探索测试」这个概念都不提**（不留小节、不写一句「将来可以…」）。

理由两条：
1. 它是**一次会话的任务书**，强绑定项目自身的文档路径（需求范围、业务规则），换了项目就没有那些路径；
2. 它依赖执行方具备**浏览器驱动与截图判读能力**——不是通用骨架能兜的承诺。

## 三、新项目要自建时去哪找参照

- **要 e2e**：Playwright 官方起步即可；关键是把「一次性环境」这件事想清楚
  （不连本机 dev 库：会污染数据、不可复现、掩盖「干净环境才暴露」的坑），
  并把测试专用配置**直接注入 CI 的 env，不建 `.env` 文件**（`.env` 一旦入库就是第二份会漂的配置真相源）。
- **要探索测试**：那就写成**该项目自己的**文档（放 `docs/` 下），把该读的项目文档路径显式列全，
  并要求执行方在能力不足时**在报告里声明缺了什么**，而不是默默跳过。

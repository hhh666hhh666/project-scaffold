# 质量策略选型指引

**这份是「要不要再加东西」的指引，不是骨架的一部分**——模板默认**不含**静态分析与 lint。

## 一、测试系统的成熟度三档

先看清自己要哪一档，别一上来就照「企业级」配。

| 档 | 有什么 | 适用 | 代价 |
|---|---|---|---|
| **基础** | 后端纯单元测试 + 前端逻辑单测与组件状态测试、`typecheck` + 构建 | 单人自用、原型、还没定型的项目 | 极低；抓不到「接起来对不对」 |
| **合格** | 上面 + 接口层（真 Spring + 真库，验契约与**数据边界**）+ 文档/待办守卫 | 有真实用户、有公开入口 | 需要 Docker；写一个 IT 的成本明显高于单测 |
| **企业** | 上面 + 端到端 + 依赖安全扫描 + 组件测试 | 多人协作、钱或数据出问题的代价高 | 维护成本陡增；CI 时间以十分钟计 |

**骨架默认落在「基础」**：后端纯 JUnit 样例与真库接口样例、前端请求层逻辑单测与一个组件状态样例、typecheck、构建，加三条文档守卫。
**建议**：第一个功能上线前补到「合格」——因为「拿别人的 id 能不能改」这类**数据边界**问题，
只有接口层抓得到，而它一旦出事就是安全事故。

## 二、静态分析与 lint：默认不做

⚠️ **模板只保留前端 `typecheck` 与后端编译器**，不加 ESLint / Checkstyle / SpotBugs / ArchUnit。

> 前端测试（Vitest）不在此列：它测的是**静默错误**（例如请求层把业务错误当成功吞掉），
> 与 lint 防的「代码漂移」是两回事——逻辑单测与组件状态测试的进入依据见生成项目的
> 「测试系统说明」里「前端逻辑单测、组件测试与 lint：取舍」一节。**lint 的立场不变。**

三条理由（都是「收益 vs 维护」的账，不是「lint 不好」）：

1. **它是多人协作防漂移的工具**。单人项目里没有「谁看谁修」那一环，
   告警要么当场被关掉，要么变成背景噪音。
2. **引入即常年红**。存量代码第一次跑必然几百条告警，于是要么整体关规则（等于没装），
   要么常年红着——而**常年红等于没有门禁**：人会养成「红了也照合」的习惯，那比不检查更糟。
3. **前端 `typecheck` 已经是必要且充分的那个门禁**（类型错误是唯一会造成线上问题的那类），
   再往上的多半是风格偏好。

## 三、真要上的最小代价路径

按这个顺序，每步都能单独停：

1. **只卡增量，不管存量**：用 diff-based 门禁（只检查本次 PR 改动的行/文件），
   存量代码一次性豁免。这是唯一能避免「引入即红」的办法。
2. **只开高价值规则**：空指针 / 资源未关闭 / SQL 注入 / 明显的并发问题。
   风格类（缩进、命名、import 顺序）交给格式化工具，不进门禁。
3. **先本地、后 CI**：先在编辑器/本地脚本里跑通一轮、把存量清到能接受，再进 CI。
   直接进 CI = 用 CI 的时间替你试错。
4. **定一个负责人**：告警归谁。没人认领的规则集会在三个月内被整体关掉。

## 四、一条相关的取舍：依赖安全扫描

骨架的 CI 里**没有**依赖扫描。要加的话：

- **只卡 PR 增量、只卡 high 及以上**——存量的语义是「别再往里加新的」，不是「仓库现在是干净的」；
- ⚠️ Maven 的依赖**不会自动进** dependency graph，要先提交一份依赖快照才扫得到；
  npm 会自动进。少了那份快照，后端就是纯盲区——「看着在扫、其实没扫到后端」比没有更危险；
- 它**不区分运行时与构建期依赖**，暴露面要自己判断。

## 五、一句话结论

**先把「合格」档的接口层补上，再考虑 lint。** 前者堵的是真实的安全与正确性缺口，
后者防的漂移在单人项目里本来就不会发生。

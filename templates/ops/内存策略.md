# 内存策略

**这份文档的前提是预设 2C2G 的小机器**（可见内存约 1870MB）。机器更大就放松，更小就得再压——
**算法是一样的，数值要按实测填**。

> **参数值的真相源是云上编排文件（compose）**——MySQL 的 `command:` 段、后端的 `JAVA_TOOL_OPTIONS`、
> 各服务的 `mem_limit`。本文只写**为什么这么定**与**怎么算出来的**；
> 若本文的数值与 compose 不一致，以 compose 为准并顺手把本文改对。

## 二、三个服务各自的策略

### MySQL：省在这里最划算

三条通用措施连同代价都写在 compose 的注释里，这里只留判据：

- **关 `performance_schema` 不影响任何业务功能**，代价是失去它的性能诊断视图；以后要做 SQL 级性能分析时临时开回来。它常常是单项最大的一笔可回收内存。
- `innodb_log_buffer_size` 与 `table_open_cache` 都容易被默认值顶高，按实际负载配。
- **`innodb_buffer_pool_size` 别压太狠**：它是 MySQL 性能的关键，压它换内存是亏本买卖。

### Spring Boot：堆只是其中一半

**这是本文最该记住的一条**：`-Xmx` 不是「这个进程最多占多少」，它只是**堆**的上限。
一个 Spring Boot 进程的**理论上限**是：

```
理论上限 ≈ -Xmx + 242MB（固定附加）
固定附加 242MB = 元空间 112 + 直接内存 32 + 代码缓存 48 + 线程栈 ~15 + JVM 自身 ~35
```

所以配 `-Xmx256m` 时，**理论上限约 498MB**——做容量规划要按这个数，不是按 256MB。
（现实高水位会更低，因为各项不会同时吃满；但规划该用前者。）

已经压过的几处（都在 `JAVA_TOOL_OPTIONS` / Tomcat 线程数里，理由见 compose 注释）：
`-Xss512k`、`-XX:TieredStopAtLevel=1`（只用 C1，省掉 C2 编译线程与大部分代码缓存）、
`-XX:ReservedCodeCacheSize=48m`、`MaxDirectMemorySize=32m`、Tomcat 工作线程封顶。

⚠️ **会进入收益递减区**：再压只剩两条路——`-Xmx` 继续降（吃掉批量导入 / 导出的峰值余量），
或上 AppCDS 类共享归档（元空间能省几十 MB，但要改 Dockerfile 重建镜像）。
**除非实测出问题，否则别继续压。**

### web（反代 + 静态文件）：可以忽略

通常只有个位数 MB，不用管。

## 三、内核级硬顶：`mem_limit`

JVM 与 MySQL 的参数只能约束「它们自己认识的内存」。真出现参数管不住的泄漏时，
`mem_limit` 让内核 **OOM-kill 掉单个容器**，而不是拖垮整机。

取值逻辑一致：**实测占用的 1.3~2.4 倍**。这是保险，不是配额——设太紧反而增加误杀风险。

## 四、要加一套新系统时怎么算

```
可给新系统的预算 = 当前 available
                 − 已有服务的增量（若共用这台 MySQL，要给它预留 ~100MB：
                    连接数上升 + 数据量增长都会让它的驻留往上走）
                 − 安全垫 175MB（防止整机贴到 swap 而触发换页甚至 OOM）
```

新系统自身的参数照抄 §二 的同口径，并满足：

```
新系统的 -Xmx + 242MB ≤ 上面算出来的预算
```

**worked example（2C2G，数值仅作示例，务必按自己的实测替换）**：

```
假设实测：整机 available 1011MB
          − 共用 MySQL 预留 100MB
          − 安全垫 175MB
        ⇒ 预算 736MB（这是**整机**能再吃下的量）

新系统自身：-Xmx + 242MB ≤ 736MB  ⇒  -Xmx 最大约 494MB
若按「还要给第二个容器留余量」再打个折，落地口径大约是 -Xmx192m ~ 256m。
```

⚠️ 加第二套系统属于一次**结构性决策**，该走一条 ADR；**未决的部分去 `docs/todo/`，不在本文排队**。

## 五、止损线（触发就该动手，别硬扛）

1. `docker stats --no-stream` 里任一容器的占用逼近它的 `mem_limit`
2. `free -m` 的 **swap 已用持续上涨**
3. `dmesg -T | grep -i oom` 出现任何一次

⚠️ **swap 有占用不等于出事**：冷页待在 swap 里反而把物理内存让给热数据，判断标准是它**涨不涨**。
同理，用 `swapoff` 把冷页读回内存是反向操作，**别做**。

## 六、日常观察命令

```bash
free -m                                                                      # 整机与 swap
docker stats --no-stream                                                     # 各容器占用与 mem_limit
docker exec ${PROJECT_NAME}-server cat /proc/1/status | grep -E 'VmRSS|Threads'   # JVM 真实驻留与线程数
```

⚠️ 后端镜像通常只有 JRE（没有 `jcmd` / `jstack`），所以 JVM 的构成只能从 `/proc` 反推——上面第三条就是那个入口。

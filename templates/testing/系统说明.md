# 测试系统说明

**目的**：讲清测试系统**为什么**是现在这个形状——分几层、每层回答什么别层回答不了的问题、能保证什么、**明确不保证什么**，以及加新功能时该补哪层测试。

**读者**：改代码前想知道「安全网在哪、这次要补什么」的人。

**真相源**：本文档是**设计意图**的真相源。**现状与清单**（有哪些测试类、CI 跑哪些 job）在 [README](./README.md) 与 `.github/workflows/`，本文档**不复制**。规则数值（阈值、字段名、响应信封形状）一律指向代码，也不复制。

---

## 一句话

**三层，每层存在的理由是「它有一个别层问不出的问题」。**

层数不是越多越好——加一层必须能说出「它独有的问题是什么」，说不出来就不该加。反过来，能被别层覆盖的也不该重复测：**同一件事只在一层验，避免两处断言互相漂**。

> ⚠️ **边界声明**：本模板只给**分层规范与同步纪律**，**不含端到端（e2e）工程的跑法**——
> 端到端强绑定具体业务场景与运行环境（前端 dev server 的监听地址、浏览器安装、一次性数据库的起法、
> 页面里的定位钩子），剥掉后所剩无几；且新项目在还没有业务之前并不需要它。
> 这是**明确不沉淀**，不是遗漏。

## 分层总表

| 层 | 回答什么问题 | 靠什么跑 | 需要机器上有什么 | 跑在哪 |
|----|--------------|----------|------------------|--------|
| **单元** | 单个类的逻辑对不对 | JUnit 5 | 无 | 任意机器 |
| **接口**（第二层的一种形态） | HTTP 契约、鉴权、**数据边界**对不对 | 真 Spring + 真 MySQL | Docker | CI / 本机（可选） |
| **服务集成**（第二层的另一种形态） | 跨组件协作、事务、**多表状态一致** | 真 Spring + 真 MySQL | Docker | CI / 本机（可选） |

第二层的两种形态**不是两个层**，是同一层的两种切入方式，区别只在「从哪里进去」：

- **接口形态**：从 HTTP 进去。问的是**约定**——响应信封统一吗、分页结构对吗、没带 token 会不会被拦、**拿别人的 id 能不能改**。
- **服务集成形态**：从 Service 进去。问的是**协作**——提交之后事务有没有回滚、几张表的状态一致吗。

怎么选：**验约定与边界走 HTTP，验数据流转直接调 Service。** 硬把两者混在一起会写出两不像的测试。

## 能保证什么 / 不能保证什么

写下来是为了**防止对它产生不切实际的期待**——尤其是「有了测试就等于都对了」这种期待。

| 维度 | 能做到 | 做不到 |
|------|--------|--------|
| 业务主链路 | ✅ 抽样验证（清单内那几条） | ❌ 穷尽组合（状态 × 来源 × 网络，列出来上千条） |
| 关键业务规则的界面表现 | ✅ 只限**写进断言的那几条** | ❌ 没写进断言的一律不管 |
| 单个类的逻辑 | ✅ 单元层枚举 | ❌ 需要库才能验的逻辑（那属接口/集成层） |
| HTTP 契约与数据边界 | ✅ 接口层专门覆盖 | ❌ 界面是否呈现 |
| UI 交互细节（悬停、禁用态、二次确认、键盘操作） | ❌ 除非法专门写 | — |
| **排版的审美与层级**（间距、重心、主次、对比） | ❌ 断言表达不了 | ❌ **零自动化保证** |
| 偶发 / 时序问题（竞态、泄漏、长时间退化） | ❌ 单次跑复现不了 | — |
| 线上运维（容器、反代、证书、备份恢复） | ❌ 在测试视野外 | 归 `docs/operations/` |

**一句话**：它是「关键逻辑的回归保险」，**不是「全面质量保证」**。

## 明确不做

这些是**已定的边界**，不是在排期的待办——写在这里是为了不再回头纠结。

| 不做 | 理由 |
|------|------|
| **端到端（e2e）跑法模板** | 强绑定具体业务场景与运行环境，剥掉后所剩无几；没有业务之前也不需要（见上面边界声明） |
| **视觉回归截图比对** | ① 逐像素差异不影响业务正确性，且这类现象开发时打开页面**当场可见**，不像静默错误；② 单人项目没有第二双眼睛审「新基线对不对」，等于自己给自己签字；③ 基线是入库的二进制、会持续膨胀，而 CI 上未必装了对应字体，界面截图永远对不齐 |
| **跨浏览器矩阵**（Firefox / WebKit） | 用户量小，Chromium 一个引擎够用，多引擎是纯成本 |
| **全量依赖扫描门禁**（把存量漏洞也一并卡住） | 存量一旦进门禁就常年红，而**常年红等于没有门禁**——人会养成「红了也照合」的习惯，那比不检查更糟。存量另有落点（`docs/todo/`） |

## 前端组件测试与 lint：取舍

两个前端工程**没有单测、没有 lint**。取舍写在明处：

- **「前端工程不引额外依赖」是刻意的形态**——保持「随手能跑」的手感，不是为了省事而漏掉。
- **组件测试与 lint 的触发条件**是「多个页面复用同一段自研逻辑、或纯逻辑密度显著上升」。
  骨架阶段不成立；等它成立了再补，并记一条 ADR。
- 在此之前，**交互路径靠人眼 + 端到端（若自建）兜**。

## 加新功能时如何同步

同步**不靠记性**，靠一张表、一条规则、一条机械守卫。

### 1. 改动 → 补哪层

| 改了什么 | 补哪层 | 具体补什么 |
|----------|--------|------------|
| 新增 / 改接口（Controller、DTO、VO） | 接口 | 响应信封、分页、错误码、鉴权、**数据边界**（拿别人的 id 来读写必须失败） |
| 核心业务规则 | 单元 **+** 服务集成 | 纯逻辑用单元；落库后的多表状态用服务集成 |
| 数据库结构（迁移脚本） | 服务集成 | 真库上跑通迁移 |
| 前端页面 / 路由 / 交互 | 端到端（若已自建） | 补一条用例，跑通用户能看见的那条路 |
| 升级 / 新增第三方依赖 | **不补**（但要看情况） | 漏洞由依赖扫描自动比增量，**不用手写测试**；但**跨 minor / major 的升级**要按上面「前端页面」「业务规则」等对应行判断——「行为是否还和以前一样」扫描管不了 |
| 只改样式 / 文案 / 排版 | **不补** | 不写新断言 |
| 类型定义 | **不补** | 已有 `typecheck` 覆盖 |
| CI / 脚本 / 部署 | **不补** | 属运维流程 |

### 2. 同一个 PR

对应测试必须进**同一个 PR**，不许「先合功能、测试下轮补」。上下文一散，补测试就永远不会发生。

### 3. 机械守卫兜底

一条 CI 检查：**每个 `module/*/controller` 至少有一个对应的测试类**。它把「新模块配了测试」从约定变成可验证事实。

⚠️ 已知局限，写在明处：**它只验「有测试类」，验不了「断言有没有到点子上」**——防遗忘的兜底，不是质量保证。

### 4. 什么不用补

反向清单同样重要，否则每个改动都会背上「必须写测试」的包袱：**只改样式 / 文案 / 排版不用补**、**只改类型不用补**（`typecheck` 已覆盖）、**只改 CI 与部署脚本不用补**（那是运维流程）。

### 5. 什么时候要动这套系统本身

**加一层、加一个新运行环境**，都属于系统变更——**必须走一条新 ADR**，不许在功能 PR 里顺手加。

### 6. 加测试**不需要改文档**

文档从不列测试清单与数量（数量会变，清单必然漂）。所以「同步」这件事的负担被压到了最低：**写了测试就跑，文档一个字都不动**。这是刻意的设计，不是疏忽。

## 本文件用到的几个词

| 词 | 定义 | 不要叫 |
|----|------|--------|
| 单元测试 | 隔离测单个类，不拉 Spring、不碰库 | — |
| 接口测试 | 走 HTTP 验约定与边界 | 不要叫「集成测试」（太含糊） |
| 服务集成测试 | 真 Spring + 真库，直接调 Service 验事务与多表流转 | 不要叫「集成测试」 |

**这几个词不进根 `CONTEXT.md`**——那里只收「本项目独有的概念」，而这些是通用技术词。
